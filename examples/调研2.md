# 超算集群用户跑作业常见的报错类型

自顶向下大致有这么几个方面：最上面是应用层（运行时）、中间是调度和资源管理（slurm、结点OS）、最下面是硬件层

- **程序运行时**
  - 加载链接库缺失
  - OOM
  - Segmentation Fault
  - 脚本编码问题（win->linux换行符）

- **Slurm端**
  - 路径错误（如可执行文件不存在等）
  - 命令参数错误（分区、节点等写错）

- **硬件**
  - 节点故障宕机
  - 节点不可达、网络故障

## 一、应用层（运行时错误）

### 1. 加载链接库缺失

**解释**：程序启动或运行中找不到依赖的 .so 动态库，常见原因是没有加载对应模块（module load）、LD_LIBRARY_PATH 未设置、或编译环境和运行环境不一致。

**例子**：程序用 Intel 编译器编译，运行时却加载了 GCC 的 libstdc++.so，导致 GLIBCXX_3.4.XX not found——表面上库“存在”，但版本符号不匹配。

**排查**：

- 用 ldd ./your_app 检查哪些库显示 “not found”。
- 用 readelf -d ./your_app | grep -E 'NEEDED|RPATH|RUNPATH' 确认程序记录了哪些依赖以及运行时搜索路径。
- 确认 LD_LIBRARY_PATH 是否包含库的实际路径。

**修复**：

- 临时方案：export LD_LIBRARY_PATH=/path/to/lib:$LD_LIBRARY_PATH。
- 推荐方案：编译时加上 -Wl,-rpath,/path/to/lib，将搜索路径写入可执行文件。
- 如果是版本符号不匹配（如 GLIBCXX_3.4.XX not found），需统一编译环境与运行环境的编译器版本，或改用静态库编译。

### 2. OOM（Out Of Memory）

**解释**：进程申请的内存超过物理内存+swap上限，被内核 OOM Killer 杀死，或 malloc 返回 NULL。常见于大数组、内存泄漏、每进程内存估算不足。

**例子**：MPI 程序在 MPI_Init 阶段就 OOM——因为每个 rank 都加载了完整数据集，而不是读取各自分片，导致节点内存瞬间被 N 份副本撑爆。

**排查**：

- 用 seff JOBID 查看作业实际内存使用峰值（MaxRSS）。
- 检查 .out 或 .err 中是否有 “oom-kill” 或 “Exceeded job memory limit” 字样。
- 在运行节点上用 dmesg | grep -i oom 确认内核层面是否触发了 OOM Killer。

**修复**：

- 增加 --mem 或 --mem-per-cpu 的值，建议设为观测峰值的 1.5–2 倍。
- 程序层面排查内存泄漏，或用更省内存的算法/数据结构。
- 注意 /tmp 和 /dev/shm 上的临时文件也计入内存消耗。

### 3. Segmentation Fault（段错误）

**解释**：程序访问了非法内存地址，常见原因包括数组越界、空指针解引用、栈溢出、跨语言接口（如 Fortran/C）参数传递错误。

**例子**：Fortran 程序里把 real*4 数组传给期望 real*8 的 C 函数，C 端按 8 字节步长读取，跑过数组边界触发段错误；数据规模小的时候“碰巧”不出错，规模一大才暴露。

**排查**：

- 用 ulimit -c unlimited 开启 core dump，然后重新运行捕获 core 文件。
- 用 gdb ./your_app core.xxx 加载 core 文件，执行 bt 查看调用栈。
- 如果程序没生成 core，可用 addr2line -e ./your_app <地址> 将报错地址翻译为源码行号。

**修复**：

- 根据调用栈定位非法内存访问位置，常见原因包括数组越界、空指针解引用、栈溢出。
- 编译时加 -g -O0 获得完整调试信息，加 -fcheck=bounds（Fortran）或 -fsanitize=address（C/C++）辅助定位。

### 4. 脚本编码/换行符问题

**解释**：Windows 下编辑的脚本（CRLF 换行）上传到 Linux 后，\r 被当作命令/变量的一部分，导致“command not found”或路径解析错误。

**例子**：Slurm 批处理脚本用 dos2unix 转换后仍然报错——原来是脚本里嵌入了一个从网页复制的不可见 Unicode 零宽字符，bash 解析变量名时包含该字符，报“bad substitution”。

**排查**：

- 用 cat -A job.sh 查看行尾，若显示 ^M$ 则为 Windows CRLF 换行。
- 报错常表现为 bad interpreter 或 command not found，变量名后带不可见字符。

**修复**：

- 运行 dos2unix job.sh 或 sed -i 's/\r$//' job.sh 将换行符转为 LF。
- 用 cat -v 检查是否有不可见的 Unicode 零宽字符，用编辑器清除。

### 5. 浮点异常（Floating Point Exception）

**解释**：整数除零、浮点下溢到非正规数触发 FPU 陷阱、或非法数学操作（如 sqrt(-1)）导致 SIGFPE。

**例子**：CFD 代码在极低马赫数下，局部密度计算趋近于零，1/rho 触发浮点异常——但只在特定网格分区边界出现，整机跑 100 次复现 1 次。

**排查**：

- 检查是否有整数除零，或对负数开方、取对数。
- 用 -ffpe-trap=invalid,zero,overflow（GCC）编译，使浮点异常触发 SIGFPE 并给出更明确的位置。
- 用 -g 编译后通过 gdb 查看异常发生的行号。

**修复**：

- 在计算前对分母、输入值做合法性检查。
- 对极端物理条件加入数值保护（如 max(rho, epsilon)）。

### 6. MPI 通信死锁/挂起

**解释**：集体通信（MPI_Allreduce、MPI_Barrier）中某个 rank 提前退出或走错分支，导致所有 rank 永远等待。

**例子**：某个 rank 遇到 MPI_ERR_TRUNCATE 后调用了 MPI_Abort，但其他 rank 还在 MPI_Recv 等待数据，整个作业挂到 walltime 超时被杀。

**排查**：

- 用 scontrol show job JOBID 确认作业状态是 RUNNING 但长时间无输出。
- 检查 MPI 报错中最开始的错误信息，后续报错往往是连锁反应。
- 用 ping 测试节点间连通性，确认免密登录配置。

**修复**：

- 确保所有 rank 执行相同数量的集体通信操作，避免条件分支导致部分 rank 跳过 MPI_Barrier。
- 多节点运行且涉及文件访问时，确认共享盘已挂载且路径一致。
- 网络波动场景可调整超时参数，如 -x UCX_UD_VERBS_TIMEOUT=30s。

### 7. 文件 I/O 错误

**解释**：读/写文件时路径不存在、权限不足、磁盘配额满、Lustre/GPFS 文件系统元数据超时等。

**例子**：作业在 Lustre 上以 O_APPEND 模式从 4096 个进程同时写一个日志文件，触发了 Lustre 的锁竞争风暴，导致 I/O 吞吐降到 KB/s，最终因文件系统超时报 Input/output error。

**排查**：

- 用 hpcquota 或 lfs quota 检查磁盘配额是否已满。
- 确认文件路径存在且当前用户有读写权限。
- 大量进程同时写同一文件时，检查是否为锁竞争问题。

**修复**：

- 清理配额或申请更多空间。
- 避免多进程同时 append 同一文件，改为各进程写独立文件或由主进程汇总。

### 8. 数值不收敛/发散（科学计算特有）

**解释**：迭代求解器不收敛、时间步长过大导致 CFL 条件不满足，虽然程序“正常退出”，但结果物理意义错误。

**例子**：作业输出正常、退出码为 0，但所有时间步的残差恒为 NaN——因为初始条件文件里某个网格的坐标写成了 1e308，在计算雅可比矩阵时溢出为 Inf。

**排查**：

- 检查输出中的残差曲线，若出现 NaN 或 Inf 则确认数值发散。
- 确认初始条件文件中没有异常大的数值（如 1e308）。
- 检查时间步长是否满足 CFL 条件。

**修复**：

- 减小时间步长或调整松弛因子。
- 对初始条件做合理性校验，过滤掉异常值。

### 9. 线程/OpenMP 问题

**解释**：线程数设置超过核心数、嵌套并行冲突、共享变量未加保护导致数据竞争，结果不确定。

**例子**：用户设置 OMP_NUM_THREADS=64，但 slurm 只分配了 16 核，OpenMP 线程在 16 核上做时间片轮转，反而比单线程慢 4 倍。

**排查**：

- 用 echo $OMP_NUM_THREADS 确认线程数设置。
- 在作业中加 hostname 和 nproc 输出，确认实际分配的核数。
- 若结果不确定，检查共享变量是否有数据竞争。

**修复**：

- 设置 OMP_NUM_THREADS 不超过 Slurm 分配的 --cpus-per-task。
- 用 -fopenmp 编译并配合 -g -fsanitize=thread（GCC）检测数据竞争。

## 二、调度和资源管理层（Slurm/结点OS）

### 10. 路径错误（可执行文件不存在）

**解释**：sbatch 脚本中写错了路径、依赖的输入文件不存在、或工作目录没有切换到预期位置。

**例子**：用户在脚本里用 cd ~/project/run1 && ./a.out，但家目录挂载延迟（autofs），cd 失败后 && 短路，作业秒退且退出码为 1，stderr 里只有 cd: No such file or directory。

**排查**：

- 查看 .out 和 .err 文件中的第一条错误信息。
- 在脚本首行加 pwd 和 ls -l 输出当前目录和文件列表。
- 用 scontrol show job JOBID 查看作业的 WorkDir 字段。

**修复**：

- 使用绝对路径，避免依赖登录时的当前目录。
- 在脚本开头显式 cd $SLURM_SUBMIT_DIR。
- 检查 --output 和 --error 路径的目录是否存在且可写。

### 11. 命令/参数错误

**解释**：分区名、QoS、节点数、任务数等参数拼写错误或超出限制。

**例子**：用户写 --ntasks=64 但忘了写 --nodes=2，Slurm 默认尝试在一个节点上放 64 个任务，而每节点只有 32 核，导致该节点 CPU oversubscribe，作业慢 10 倍。

**排查**：

- 提交时若报 Invalid partition 或 Requested node configuration is not available，检查分区名和资源请求是否超出节点能力。
- 用 sinfo 查看可用分区和节点配置。
- 用 scontrol show partition <name> 查看分区的约束条件。

**修复**：

- 核对 --partition、--account、--qos 的拼写和有效性。
- 确认 --ntasks、--cpus-per-task、--mem 的组合不超过节点物理资源。
- 若申请了特殊 constraint（如 avx512），确认有节点满足条件。

### 12. 超时被杀（Time Limit Exceeded）

**解释**：作业超过 --time 设定值被 Slurm 强制终止，信号为 SIGTERM 或 SIGKILL。

**例子**：checkpoint 文件写在 /tmp 里，作业超时被杀后重启，但 /tmp 已被清理，之前 20 小时的中间结果全部丢失。

**排查**：

- 错误信息中会有 DUE TO TIME LIMIT。
- 用 seff JOBID 查看运行时长与请求时长的对比。
- 检查分区是否有默认时间上限（如某些集群默认 4 小时）。

**修复**：

- 增大 --time 值，或拆分作业为可恢复的多个小作业。
- 在程序中加入检查点（checkpoint）机制，定期保存中间结果。
- 注意检查点不要写在 /tmp，因为作业被杀后可能被清理。

### 13. 内存超限被杀

**解释**：Slurm 的 cgroup 限制每作业可用内存，超过限制即被杀（不等于内核 OOM）。sacct 里状态为 OUT_OF_MEMORY。

**例子**：用户申请了 64GB 内存，程序本身只用 40GB，但 fork 了 8 个子进程做后处理，每个子进程继承父进程的地址空间（copy-on-write 未生效），瞬时内存超限被杀。

**排查**：

- sacct -j JOBID 查看 State 是否为 OUT_OF_MEMORY。
- 某些 Slurm 版本可能只报 FAILED 而不明确标注 OOM，需用 dmesg 在节点上确认。
- 用 seff 对比请求内存与实际峰值。

**修复**：

- 增加 --mem 或 --mem-per-cpu。
- 如果是 fork 导致的内存翻倍，考虑用 --mem-per-cpu 按每进程内存计算，或改用 MPI_Comm_spawn 等机制。

### 14. 排队/资源不足（Pending 时间过长）

**解释**：资源暂时无法满足，如节点数太多、GPU 卡被占满、分区维护等。squeue 里显示 (Resources) 或 (Priority)。

**例子**：用户申请了 --constraint=avx512，但集群里只有 4 台节点满足条件且都在维护，作业 pending 48 小时后用户才发现。

**排查**：

- squeue -u $USER 查看作业的 pending 原因（REASON 列）。
- 常见原因：Resources（资源不足）、Priority（优先级低）、Dependency（依赖未满足）、ReqNodeNotAvail（节点维护）。
- 用 sinfo -p <partition> 查看分区空闲资源。

**修复**：

- 调整资源请求到有容量的分区。
- 减少节点数或核数要求，缩短 walltime 以提高调度成功率。
- 如果是依赖问题，用 scontrol show job JOBID 查看依赖链。

### 15. 作业启动失败（Prolog/Epilog 错误）

**解释**：节点上的 prolog/epilog 脚本（如健康检查、环境初始化）失败，导致作业还没跑就被取消。

**例子**：某节点的 prolog 脚本里用 df /scratch 检查磁盘，刚好 /scratch 在做 Lustre 恢复而挂起，超时后作业被 NODE_FAIL。

**排查**：

- 用 scontrol show job JOBID 查看 Reason 字段，或 sacct 查看 State 是否为 NODE_FAIL。
- 登录节点用 scontrol show node <nodename> 查看节点状态和原因。

**修复**：

- 如果是节点被 drain，联系管理员或改用其他节点。
- 如果是 prolog 脚本超时，等待文件系统恢复后重新提交。

### 16. 环境变量继承问题

**解释**：交互式 shell 里能跑的程序，在 sbatch 里跑不了，因为 sbatch 默认不继承当前 shell 的全部环境变量。

**例子**：用户在 .bashrc 里设置了 export MY_LIB_PATH，交互式运行没问题，但 sbatch 脚本里没有 source ~/.bashrc，提交后报 libmy.so not found。

**排查**：

- 在 sbatch 脚本中加 env | sort 输出所有环境变量，与交互式 shell 对比。
- 确认 module list 在作业脚本中是否与登录时一致。

**修复**：

- 在脚本开头显式 source ~/.bashrc 或 module load 所需模块。
- 用 sbatch --export=ALL 传递所有环境变量。
- 多节点 MPI 运行时，用 -x LD_LIBRARY_PATH -x PATH 将环境变量传递到所有节点。

### 17. 节点状态异常（drain/down）

**解释**：节点被管理员 drain（排空）或自动 down，新作业不会分配到该节点。

**例子**：节点温度传感器误报，Slurm 自动将节点标记为 drain，但用户看到 sinfo 里节点状态是 drain 却不知道原因，作业一直 pending。

**排查**：

- sinfo -R 查看所有异常节点及其原因。
- scontrol show node <nodename> 查看详细状态。

**修复**：

- 管理员 drain 的节点需联系管理员恢复。
- 如果是自动 drain，通常是硬件或系统问题，需运维介入。

## 三、硬件层

### 18. 节点故障宕机

**解释**：节点突然重启、kernel panic、硬件错误（MCE）、电源故障。作业被中断，sacct 显示 NODE_FAIL。

**例子**：一组作业连续三次在同一个节点上失败，排查发现该节点的 ECC 内存在特定地址持续报可纠正错误（CE），当作业恰好分配到该区域内存时触发 MCE 宕机。

**排查**：

- sacct -j JOBID 查看 State 是否为 NODE_FAIL。
- 登录节点用 dmesg 查看是否有 MCE（Machine Check Exception）或 kernel panic 记录。

**修复**：

- 重新提交作业，Slurm 会自动避开故障节点。
- 如果同一节点反复导致作业失败，用 scontrol update NodeName=<node> State=DRAIN Reason="..." 手动标记并通知管理员。

### 19. 节点不可达/网络故障

**解释**：IB/以太网故障导致节点间通信中断，MPI 作业报连接超时或挂起。

**例子**：InfiniBand 交换机上某端口光模块老化，信号强度波动，导致该节点上 MPI 作业随机出现 ibv_post_send failed: Connection timed out，但 ping 测试完全正常。

**排查**：

- 从计算节点 ping 其他节点，检查连通性。
- 用 ibstat（InfiniBand）检查端口状态和链路速率。
- MPI 报错中关注 “Destination is unreachable” 或 “Connection timed out”。

**修复**：

- 检查网卡是否被 down：ip a 确认接口状态。
- 如果是 IB 光模块老化，需管理员更换硬件。
- 临时缓解可调整 MPI 超时参数，但根本方案是硬件维修。

### 20. 磁盘/文件系统故障

**解释**：共享存储（Lustre/GPFS/NFS）宕机、磁盘坏块、RAID 降级，导致读写失败或 I/O 极慢。

**例子**：Lustre 的某个 OST（对象存储目标）因为 SATA 线缆接触不良导致频繁 I/O error，被系统标记为 degraded，落在该 OST 上的文件读写全部超时。

**排查**：

- df -h 和 lfs df 检查文件系统挂载状态和空间。
- dmesg | grep -i "I/O error" 查看是否有磁盘读写错误。
- Lustre 场景用 lctl get_param osc.*.ost_conn_uuid 检查 OST 连接状态。

**修复**：

- 如果某个 OST degraded，落在该 OST 上的文件会 I/O 超时。联系管理员恢复，或将数据迁移到其他路径。
- 避免在作业中频繁访问同一 OST 上的小文件。

### 21. GPU 故障（如 ECC 错误、掉卡）

**解释**：GPU 显存 ECC 错误超过阈值、NVLink 断开、驱动崩溃，导致 CUDA 程序报错。

**例子**：GPU 显存某区域出现不可纠正 ECC 错误，CUDA 程序每次 cudaMemcpy 到该区域都返回 cudaErrorIllegalAddress，但 nvidia-smi 显示 GPU 状态正常，直到运行 nvidia-modprobe -m 才暴露错误。

**排查**：

- 在分配了 GPU 的节点上运行 nvidia-smi，检查 GPU 状态和 ECC 错误计数。
- 用 nvidia-smi -q -d ECC 查看显存 ECC 错误详情。
- CUDA 程序报错中关注 cudaErrorIllegalAddress 或 cudaErrorECCUncorrectable。

**修复**：

- 如果 ECC 不可纠正错误持续出现，该 GPU 需要下线维修。
- 重新提交作业，Slurm 会避开故障 GPU。
- 临时缓解：设置 CUDA_LAUNCH_BLOCKING=1 使报错位置更精确。

### 22. 散热/温度问题

**解释**：节点过热导致 CPU/GPU 自动降频甚至强制关机。

**例子**：夏季机房空调故障，节点进风口温度 35°C，CPU 触发热保护降频到 800MHz，作业运行时间从 2 小时变成 8 小时，最终超时被杀。

**排查**：

- sensors 或 ipmitool sdr 查看节点温度。
- 用 seff 发现作业运行时间远超预期，CPU 频率可能被降频。
- dmesg | grep -i thermal 查看热保护事件。

**修复**：

- 如果是机房空调问题，需管理员处理。
- 临时方案：在温度较低的时段运行作业，或减少每节点负载。

### 23. 电源故障

**解释**：PDU 跳闸、UPS 切换失败、单路电源掉电导致节点突然断电。

**例子**：机柜的 A 路电源维护，节点切到 B 路供电，但 B 路 PDU 额定电流不足，满载运行时跳闸，整个机柜节点瞬间断电。

**排查**：

- 节点突然断电且无软件日志，dmesg 中无记录，指向电源问题。
- 检查该机柜其他节点是否同时宕机。

**修复**：

- 联系机房管理员检查 PDU/UPS。
- 重新提交作业。

## 一、Slurm的故障排查

| 工具 / 命令 | 粒度 | 是否需要特权 | 用途 |
| --- | --- | --- | --- |
| sacct -j <job_id> | 集群 | 否 | 查看已完成作业的详细状态、退出码和资源使用情况。 |
| seff <job_id> | 集群 | 否 | 获取作业失败原因的摘要，能区分是 OOM、超时还是其他错误。 |
| scontrol show job <job_id> | 集群 | 否 | 查看作业的详细配置和状态信息。 |
| 检查资源使用 | 集群 | 否 | 怀疑内存问题时，用 sacct 查看 MaxRSS（最大物理内存使用量）和 ReqMem（申请的内存量），对比MaxRSS和 ReqMem，判断是否接近或超出申请值。 |
| sstat | 单节点 / 集群 | 否 | 查看正在运行的作业或作业步骤的实时状态与资源消耗（如CPU、内存），可看作 sacct 的实时版本。 |
| scontrol show node <nodename> | 单节点 / 集群 | 否 | 查看节点的详细状态，包括 State（如 drain、down）、Reason（如 Not responding）、FreeMem 等，用于判断节点是否健康。 |
| sinfo -R | 集群 | 否 | 列出所有处于 drain、down、fail 等状态的节点及其原因，快速定位问题节点。 |
| squeue -j <job_id> -o "%.10i %.8T %.10r %.10M %.6D %R" | 集群 | 否 | 查看作业的详细状态，特别是 Reason 字段，用于分析作业为何处于 PENDING（如 Resources、Priority、NodeDown）或 FAILED 状态。 |
| scontrol show job <job_id> \| grep -E "StdOut\|StdErr\|WorkDir" | 集群 | 否 | 确认作业的标准输出/错误文件路径及工作目录，用于排查输出丢失或路径错误问题。 |
| sdiag | 集群 | 否 | Slurm 调度诊断工具，可查看调度器内部统计信息，用于排查调度延迟或异常。 |
| sreport | 集群 | 否 | 从 Slurm 会计数据生成资源使用报告，可用于分析集群整体利用率或特定用户/账户的历史趋势。 |
| sacctmgr show assoc | 集群 | 通常需要管理员权限 | 查看账户和用户关联信息，用于排查 InvalidAccount 等提交失败问题。 |

**组合排查思路**

在实际排查中，建议组合使用这些工具。例如：

- **定位问题节点**：先用 sinfo -R 找到被 drain 的节点。
- **分析节点原因**：再用 scontrol show node <nodename> 查看具体的 Reason（如 Not responding）。
- **检查节点连通性**：在确认节点状态后，可进一步在节点上检查 slurmd 服务状态和网络连通性（如 ping、nc -zv <node> 6818）。
- **分析作业状态**：对于失败的作业，通过 squeue 或 scontrol show job 查看其状态和 Reason，再结合 sacct 的详细字段（如 State、ExitCode）定位失败原因。

## 三、源码 / 二进制分析工具

| 工具 / 命令 | 粒度 | 是否需要特权 | 用途 |
| --- | --- | --- | --- |
| Valgrind (Memcheck) | 单节点 | 否 | 动态二进制分析工具，无需重新编译即可检测内存越界、使用未初始化内存、内存泄漏等问题。运行时有 10-50 倍性能损耗，适合在测试或 CI 阶段使用。 |
| AddressSanitizer (ASan) | 单节点 | 否 | 编译时插桩工具，需在编译时添加 -fsanitize=address 标志。检测速度比 Valgrind 快，适合开发阶段。 |
| DUMA | 单节点 | 否 | 通过预加载库的方式检测缓冲区溢出和下溢。它利用 MMU 保护内存页，能在非法访问发生的精确指令处停止程序，便于调试定位。 |

## 四、其他补充手段

| 工具 / 命令 | 粒度 | 是否需要特权 | 用途 |
| --- | --- | --- | --- |
| LogSage（NVIDIA 开源） | 集群 | 否 | 基于 LLM 的工具，自动从 Slurm 作业日志中提取错误、归因根因，并建议恢复策略，适合大规模集群日志分析。 |
| GPU 指标冻结监控（如 Prometheus + DCGM-Exporter） | 集群 | 否 | 部分 GPU 静默故障（如 GSP 固件超时）不触发 XID 错误，但会导致 GPU 指标“冻结”（功耗、温度、时钟等不再变化）。可通过监控关键指标的标准差进行告警。 |

## 五、组合排查思路示例

排查故障时，建议将上述工具组合使用。以作业返回 **137（SIGKILL）** 为例：

- **节点层**：检查 dmesg，确认是否为 OOM Killer 所为。
- **Slurm 层**：结合 sacct 和 seff，确认作业的资源使用（尤其是 MaxRSS）和退出状态。
- **应用层**：若怀疑代码内存问题，使用 Valgrind 或 ASan 在测试环境复现并定位。

对于 GPU 作业，XID 错误码是重要的排查线索。例如，XID 79（GPU 掉总线）通常指向硬件故障，可能需要 RMA；而 XID 31（MMU fault）则更可能由用户代码的越界访问引起。

## 六、具体场景排查流程图：作业因 OOM 被杀死

```text
              │ sacct -j <job_id>                                                            │
              │   --format=JobID,State,ExitCode,MaxRSS,ReqMem   │
              └───────────────────────────────┘
                                                         │
              ┌──────────────┴───────────────┐
              ▼                                                                                    ▼
   ┌─────────────────────┐        ┌─────────────────────┐
   │ MaxRSS 接近 ReqMem                   │        │ MaxRSS 远低于 ReqMem               │
   │ 或 seff 提示 OOM                            │        │ 且无 OOM 提示                               │

   │ journalctl -k                                       │        │ - 网络/MPI 通信故障                       │

   └─────────────────────┘
                               │
                               ▼
   ┌─────────────────────────────────────────────┐
   │ 步骤 3：区分 OOM 类型                                                                                    │
   │ - cgroup OOM：Slurm cgroup 限制触发                                                            │
   │ - 系统 OOM：节点整体内存不足，OOM Killer 介入                                     │
   │ 查看 dmesg 中 "Killed process" 及 "oom-kill"                                                   │
   └─────────────────────────────────────────────┘

   │ - 若为 MPI 聚合内存过高：                                                                               │
   │   调整每节点 rank 数或 --mem-per-cpu                                                               │
   │ - 若为 GPU 显存 OOM：                                                                                    │
   │   检查 nvidia-smi、调整 batch size                                                                     │
   └─────────────────────────────────────────────┘
                             │
                             ▼
   ┌─────────────────────────────────────────────┐
   │ 步骤 5：修复与验证                                                                                           │
   │ - 提高 --mem 或 --mem-per-cpu                                                                          │
   │ - 优化代码，修复内存泄漏                                                                                │

   └─────────────────────────────────────────────┘
```

**关键判断点说明：**

- MaxRSS **vs** ReqMem：若 MaxRSS 非常接近 ReqMem，说明作业确实撞到了申请的内存上限，优先考虑提高内存申请。
- dmesg **中的 OOM 记录**：若看到 Out of memory: Killed process <pid> (<job>)，即可确认是 OOM Killer 所为。若无此记录，则 137 可能来自 Slurm 自身的 cgroup 限制或其他信号。
- **区分 cgroup OOM 与系统 OOM**：cgroup OOM 只影响该作业，系统 OOM 可能影响节点上其他作业，需检查节点整体内存压力。
- **GPU 显存 OOM**：与主机内存 OOM 不同，需通过 nvidia-smi 或框架日志（如 PyTorch 的 CUDA out of memory）确认，调整 batch size 或模型并行策略。
